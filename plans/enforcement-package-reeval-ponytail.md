# Enforcement package over-engineering audit (ponytail)

Skill invoked: `ponytail:ponytail-audit` (repo-wide over-engineering audit mode), scoped to `packages/enforcement`. Intensity: the audit skill has no lite/full/ultra dial of its own; it ran at its default discipline (ranked findings, biggest cut first, one line each, tag + what-to-cut + replacement + path). Scope was over-engineering and complexity only. Correctness, security, and performance were held out of scope per the skill's boundaries.

Read in full: every `.ts`/`.sh` under `packages/enforcement` (`src/`, `hooks/`, `examples/`), `package.json`, `README.md`, `tsconfig.json`; the consumer side in `packages/cli/src/cli/index.ts`; and the shared contract in `packages/shared/src/{index.ts,harness/contract.ts,harness/resolve.ts}`. Cross-checked who imports what with grep.

## What the package is

Enforcement authors deterministic discipline gates (a PreToolUse hook that denies a tool call), wires them into a harness's hooks file, and emits a `gate.denial` event into Feedback's local SQLite store across the published store-write contract (without importing Feedback). The package carries a command facade (`src/cli/index.ts`), a pure gate-hooks planner (`src/install/gate-hooks.ts`), the published gate-command builders (`src/install/gate-commands.ts`), a clone-path safety check (`src/install/clone-path.ts`), the harness-home resolver (`src/harness.ts`), the store-write seam (`src/denial-store.ts`), the denial emitter (`hooks/emit-denial.ts`), and three reference gates in `examples/`.

## Headline

The package is mostly lean and well-factored; the planner and store-write seam are doing real, non-duplicated work. The clear cuts are a dead public command surface (`wireGates`/`unwireGates` exported but never dispatched), one belt-and-suspenders dedup layer that cannot fire given the catalog, and small reimplemented helpers. The two POSIX-shell example gates are a real native-Windows-first gap, but they are not over-engineering: they are a missing port, so they are flagged as a note, not a cut. Suspected legacy multi-repo artifacts (`clone-path.ts`, `harness.ts`) turned out to be load-bearing in the monorepo, so they stay.

## Ranked findings (biggest cut first)

1. `delete:` the `wireGates` / `unwireGates` exported command surface and their `WireGatesOptions` / `UnwireGatesOptions` interfaces. The unified `regimen` CLI dispatches only `install`/`update`/`uninstall`/`status`/`daemon`/`assess`/`evidence`/`list` (`packages/cli/src/cli/index.ts:599-625`), imports only `install`, `uninstall`, `GateId` from the package (`packages/cli/src/cli/index.ts:46-50`), and the CLI's own comment records the wiring verbs as collapsed-away internal steps (`packages/cli/src/cli/index.ts:16-18`). The only production callers of `wireGates`/`unwireGates` are enforcement's own `install`/`uninstall` one file over. Replacement: fold the two bodies into `install`/`uninstall` as private helpers (or inline them), drop the two `export` keywords and the two options interfaces, keep only `install`/`uninstall` exported. The standalone wire/unwire verb only made sense in the former standalone `regimen-enforcement` repo where you ran `wire-gates` by hand; the README still documents that hand-run form (`packages/enforcement/README.md:23-28`), which is now the only thing keeping the surface alive. [packages/enforcement/src/cli/index.ts:142-243]

2. `yagni:` the second dedup layer in `buildGateLeaves`: the `seenBasenames` set plus the entire `commandBasename` helper (the quoted-path regex, the split-on-whitespace fallback, the quote-stripping). It guards against "two gate ids resolving to the same script file," but the catalog is three ids mapped to three distinct scripts (`rm-rf-gate.ts`, `em-dash-gate.sh`, `inline-message-guard.sh`), so a basename collision is structurally impossible and the union-by-id dedup (`desiredGateIds`, catalog order) already prevents double-wiring. Replacement: drop `seenBasenames`/`commandBasename` and let `desiredGateIds` be the single dedup. If you want to keep the property enforced, a one-line unit assertion that the three script basenames are distinct replaces the runtime machinery. [packages/enforcement/src/install/gate-hooks.ts:122-135, 223-241]

3. `shrink:` `asHarness`, `resolveDataDir`, `dataDir`, `Harness` are imported into `denial-store.ts` only to be re-exported (`packages/enforcement/src/denial-store.ts:16-30`) so that `emit-denial.ts` and the conformance test pull "harness + data dir + builder" from one module. That convenience re-export barrel adds an indirection hop for two consumers. Replacement: have `emit-denial.ts` import `asHarness`/`dataDir` straight from `@regimen/shared` (it already imports `appendGateDenial`/`buildGateDenialLine` from `denial-store.ts` for the seam-owned pieces) and drop the pass-through re-export block. Minor; keep if the single-import ergonomics are valued, but it is four symbols of indirection with no logic. [packages/enforcement/src/denial-store.ts:16-30]

4. `shrink:` `readString` is hand-rolled twice, once in `hooks/emit-denial.ts:37-43` and again (alongside `asRecord`) in `examples/rm-rf-gate.ts:36-47`, and `parsePayload`/`readHookPayload` are near-identical JSON-with-empty-fallback parsers in those same two files (`emit-denial.ts:46-57`, `rm-rf-gate.ts:54-61`). These are small, but they are the same untrusted-payload field-read pattern copied across the package edge. Replacement: a single tiny `readString(source, key)` helper next to the seam (or in `@regimen/shared` if Feedback's capture edge wants it too) imported by both; the parse-empty-as-`{}` reader likewise. Weigh against the deliberate "Enforcement never couples to Feedback" stance: the duplication ACROSS the store-write seam (do not import Feedback's reader) is intentional and stays; the duplication WITHIN this package (`emit-denial.ts` vs `rm-rf-gate.ts`) is not, and is the cut. [packages/enforcement/hooks/emit-denial.ts:37-57, packages/enforcement/examples/rm-rf-gate.ts:36-61]

5. `shrink:` `describeChange` (`packages/enforcement/src/cli/index.ts:122-125`) is a one-line `\`gate ${c.id} on ${c.event}\`` template wrapped in a named function with a docblock, called only from the print loops in `wireGates`/`unwireGates`. If finding 1 folds those bodies inline, this collapses with them. On its own it is a trivial wrapper that could be the template literal at its two call sites. [packages/enforcement/src/cli/index.ts:122-125]

## Verified-and-keep (suspects that are NOT over-engineering)

- `keep:` `src/install/clone-path.ts` (`assertSafeClonePath`). Suspected multi-repo artifact; it is not. It is imported by both `gate-commands.ts:14` (so a direct CLI consumer validates) and `gate-hooks.ts:20`, and the docblock correctly explains it lives in its own file to break a real circular import (gate-hooks imports gate-commands, so the shared helper cannot sit in gate-hooks). The character set it rejects (`" $ \` \\` plus control chars, everything else literal inside double quotes) is correct for the double-quoted POSIX-shell interpolation the gate commands build, and it is genuinely exercised. No stdlib ships a "safe-inside-double-quotes" predicate. Keep as-is. [packages/enforcement/src/install/clone-path.ts:21-34]

- `keep:` `src/harness.ts` (`resolveHarnessHome`). Suspected duplication of the shared contract; it is not. The shared contract carries the DATA (`configHome.envVar`, `configHome.defaultSubdir`) but exposes no resolver that applies the env-override-else-default-subdir POLICY against a passed-in env and home. This 9-line function is that policy, and it is the only place it lives (the CLI's `resolveTarget` calls it). It is pure, injectable, and not restated elsewhere. Keep. [packages/enforcement/src/harness.ts:13-21]

- `keep:` the Copilot `versioned-command-leaves` gate path (`planVersionedGateHooks`, `planVersionedGateHooksRemoval`, `assertVersionedWellFormed`, `VersionedHooksFile`). It LOOKS speculative because the shared contract's prose says "Enforcement's gate-install planner still writes only nested-matcher-groups" (`packages/shared/src/harness/contract.ts:38-39, 100-102`), but the code at `gate-hooks.ts:356-363` actually branches on `format === "versioned-command-leaves"` and the CLI install loop reaches copilot via `--all`. The path is live and reachable, not dead flexibility. The finding here is a documentation drift (the shared contract comment is stale), which is out of scope for this over-engineering pass; route it to a docs fix. Keep the code. [packages/enforcement/src/install/gate-hooks.ts:287-324, 372-392]

- `keep:` the `GateProfile` / `GATE_PROFILES` table (`gate-hooks.ts:79-89`). One entry per harness with two real divergences (`preToolEvent` differs across all four harnesses, `needsNameMatcher` is true only for Gemini). This is data with four distinct rows that the planner genuinely branches on, not a single-implementation abstraction. Keep.

## Out of scope but worth a note (not a cut)

- The two POSIX-shell example gates (`examples/em-dash-gate.sh`, `examples/inline-message-guard.sh`) plus the `SHELL_GATES` jq-preflight (`src/cli/index.ts:38, 133-140`) and the `win32` skip in `install`/`uninstall` (`src/cli/index.ts:268-273, 307-312`) together mean two of the three gates do not run on native Windows, which sits against the project's native-Windows-first claim. This is a missing port, not over-engineering: there is no redundant code to delete, there is functionality absent. Right move is a real ticket to port the em-dash and inline-message rules to a portable runtime (the `rm-rf` gate is already TS-under-bun and cross-platform), after which the `win32` skip, the `SHELL_GATES` set, and the jq preflight all disappear. Flagging, not cutting.

## Net

net: roughly -120 to -160 lines, -0 deps possible. The biggest single cut is the dead `wireGates`/`unwireGates` public surface (finding 1), then the basename-dedup machinery (finding 2). No dependency can be dropped: the only runtime dependency is `@regimen/shared` (workspace), which is load-bearing, and the dev dependencies are the standard lint/type/test toolchain. The package is close to lean; these are real shavings, not a teardown.
