# Guidance respond-step helper: forms taxonomy and skill design

> Design doc for the respond-step helper, the Guidance-side act-beat operator skill. It is the same species of artifact as the two bundled Feedback skills (`feedback-evidence`, `feedback-judgment`): Regimen's own infrastructure, bundled and installed by Regimen, that lets the agent drive Regimen's loop in conversation. This one serves beat 2 (act) on the Guidance side. Part 1 enumerates the full breadth of Guidance forms (the design input). Part 2 designs the skill at a high level. Grounded in `docs/mental-model.md` section 5, ADR-0013, ADR-0002, the PRD, `DOMAIN-LANGUAGE.md`, and the two existing operator skills. Read-only investigation, no code changed.

## Framing carried in (locked, not relitigated)

Feedback is the center; Guidance and Enforcement are the two response levers acted with in beat 2 of the see / act / validate loop. The cut between the levers is mechanism, not form: Guidance is any advisory offering the agent is *asked* to use and may ignore; Enforcement is any deterministic mechanism that *removes* the choice. Regimen points at Guidance content, it never supplies it: the respond-step helper helps the user locate or author their own move, and it never ships a catalog of moves. An operator skill operates Regimen's own loop; it is not lever content. This helper is the operator skill for the Guidance act, exactly as the two Feedback skills are the operator skills for the see beat, and it mirrors their shape and install path. Guidance is per-harness and per-model: a form that is a non-issue on one CLI or model can be a recurring problem on another, so the same Feedback pattern resolves to different moves depending on the harness and model in play.

# Part 1: The taxonomy of Guidance forms

A Guidance move is anything advisory the engineer puts in front of the agent so the agent is *asked* to behave differently, where the agent could still choose not to. The taxonomy below groups the forms by where the advice lives and how the agent encounters it. Each entry gives: what it is; the kind of recurring Feedback pattern it best answers; how it is enacted (the concrete action); and whether Regimen ships it, points at it, or the user builds it. Across the whole taxonomy the answer to "does Regimen ship it" is almost always "points" or "user builds": Regimen ships only its own operator skills, never lever content, so "ships" never appears below for a Guidance move itself.

## The mechanism boundary (read before the forms)

Everything below is on the advisory side: the model can still choose. The moment a form removes the choice it has crossed into Enforcement and is excluded from this taxonomy. The boundary is drawn by mechanism, so the same surface can appear on both sides depending on how it is wired. A `CLAUDE.md` line that says "prefer pnpm" is Guidance (advisory). A pre-commit hook that rejects a commit using npm is Enforcement (deterministic). An MCP server the agent *may* call for retrieval is Guidance; a permission gate that *blocks* a tool unless a condition holds is Enforcement. An output-style preference the agent is asked to honor is Guidance; a schema-constrained output that the harness will not emit unless it validates is Enforcement. A subagent the agent may delegate to is Guidance; a CI check that fails the build is Enforcement. The recurring tell: if the artifact can be ignored by a sufficiently determined or distracted model and the work still proceeds, it is Guidance; if the work cannot proceed until the artifact is satisfied, it is Enforcement. The helper must hold this line, and when the honest answer is the deterministic side it hands off rather than dressing an Enforcement need as a Guidance move (see Part 2 boundaries).

## Group A: Standing context and instructions (always-loaded advisory text)

These are files the harness loads into context automatically, so the agent encounters them on every turn without being asked. They are the cheapest Guidance to author and the easiest to over-fill (an instruction file that grows unbounded dilutes every line in it), so the relevant tradeoff the helper must weigh is signal density, not just whether the line exists.

- **Standing-instruction line in the project or global instruction file** (`CLAUDE.md`, `AGENTS.md`, `GEMINI.md`, `.cursorrules`, `.github/copilot-instructions.md`, and the per-harness equivalents). What it is: a durable rule the harness loads on every turn, scoped to a repo or to the user globally. Best answers: a small, stable, always-relevant correction that recurs across many conversations (a tool preference, a naming convention, a phrasing rule, a "never do X" line). Enacted: edit the file, add one dense line under the right heading; choose project-scope versus global-scope by whether the rule is repo-specific or universal. Regimen: points (names the file and the scope; the user writes the line).
- **A focused section added to an existing instruction file.** What it is: a small grouped block (a "Testing" or "Commits" subsection) rather than a single line, when the pattern needs several related rules. Best answers: a recurring cluster of related corrections that belong together (a whole commit-message discipline, a whole test-writing posture). Enacted: edit the file, add a short headed subsection; keep it dense. Regimen: points.
- **A context-priming doc the agent is pointed at** (`CONTEXT.md`, `ARCHITECTURE.md`, a domain glossary, an ADR set, a `DOMAIN-LANGUAGE.md`). What it is: a reference document the agent is *asked* to read when relevant, carrying domain facts, vocabulary, and prior decisions, rather than a per-turn rule. Best answers: a recurring pattern of the agent misusing project vocabulary, re-deriving settled decisions, or missing domain constraints (drift and "wrong approach" corrections rooted in missing context). Enacted: author or extend the doc, and add a one-line pointer to it in the standing instruction file so the agent knows to consult it. Regimen: points (and note: Regimen's own repo *uses* this form heavily, which is prior art, not Regimen supplying the user's content).
- **Memory or persistent-context file edits** (a `MEMORY.md`, an auto-loaded memory directory, a harness's own memory store). What it is: durable cross-session notes the harness re-loads after compaction or on the next session. Best answers: a pattern where hard-won context is lost between sessions and the agent repeats a resolved mistake or re-asks an answered question. Enacted: edit the memory file or append a memory entry; keep it under the auto-load budget. Regimen: points. Boundary note: this is the closest Guidance form to Feedback's own job, but it is still Guidance because it changes what the agent is *asked* to remember, not what is measured.

## Group B: Invokable advisory units (named things the agent chooses to pull in)

These are discrete, named artifacts the agent invokes on demand rather than loading every turn. They cost nothing until used, so they are the right home for guidance that is heavy, situational, or procedural. This is the group the original "skills" naming pointed at, widened.

- **A skill** (a `SKILL.md` with frontmatter plus a procedure, discovered by the harness and invoked by name or by description match). What it is: a packaged procedure or discipline the agent runs when its trigger matches. Best answers: a recurring multi-step discipline the agent keeps doing inconsistently or skipping (a TDD loop, a review-gate routine, a planning method, a delegation habit). Enacted: find an existing one and install it, or author a new one with the LLM, then install it under the harness's skills subdirectory. Regimen: points (find) or user builds (author); Regimen never ships the discipline itself, only the helper that helps locate or write it.
- **A slash command / custom command** (a harness-defined named command that expands to a prompt or runs a workflow). What it is: a short invocable that injects a templated instruction or kicks off a known sequence. Best answers: a recurring task the engineer keeps typing out by hand the same way, or a workflow the agent should run identically every time it is asked. Enacted: define the command in the harness's command directory (a prompt file or config entry); for some harnesses this is the same shape as a skill, for others a distinct mechanism. Regimen: points / user builds.
- **A subagent or agent definition** (a named specialized agent with its own scope, tools, and prompt, that the main agent may delegate to). What it is: a delegable persona the agent can hand a bounded piece of work to. Best answers: a recurring pattern where the main conversation balloons because work that should have been delegated stayed in-thread (the work-router pattern), or where a class of task wants a different posture or tool set. Enacted: author an agent definition file (system prompt plus tool/scope config) in the harness's agents directory; or point at an existing one. Regimen: points / user builds. Note: the work-router skill is the canonical Guidance instance and lives in this group's neighborhood (it is a delegation discipline expressed as a skill).
- **A prompt template or snippet library** (reusable prompt fragments, a templated kickoff prompt, a saved instruction block the engineer pastes or the agent expands). What it is: parameterized advisory text reused across conversations. Best answers: a recurring "prompt clarity" pattern where the engineer's framing is inconsistent and the agent's first move is often wrong because the ask was underspecified. Enacted: write the template into a snippet store, a command, or a doc the agent is pointed at; the move is to make the good framing reusable rather than retyped. Regimen: points / user builds.
- **A checklist or reference example the agent is asked to follow** (a worked example, a golden-path file, a "do it like this" reference, a definition-of-done checklist). What it is: a concrete exemplar or list the agent consults to match a known-good shape. Best answers: a recurring "omission" or "quality" pattern where the agent produces structurally-right-but-incomplete output (forgets a step, misses an edge case, diverges from an established shape). Enacted: write the checklist or designate the reference example, and point the agent at it (inline in an instruction file or as a doc). Regimen: points / user builds.

## Group C: Reachable capabilities (tools and sources the agent may use)

These are not text the agent reads; they are capabilities the agent is *enabled and encouraged* to reach for. They are advisory in the sense that the agent still chooses whether and when to use them. (Provisioning a capability was deliberately folded into Guidance rather than made a fourth instrument; this group is that fold.)

- **An MCP server made available to the agent** (a Model Context Protocol server exposing tools or resources the agent may call). What it is: a capability surface (a database, an API, a doc system, a browser) the agent can invoke when relevant. Best answers: a recurring pattern where the agent works from stale or guessed information because it had no way to fetch the truth (re-deriving API shapes, guessing schema, hallucinating config). Enacted: install and register the MCP server in the harness's config, and optionally add a standing-instruction line telling the agent when to prefer it. Regimen: points / user builds (the server is external; Regimen names it as a move, it does not host or ship it). Boundary note: making a server *available* is Guidance; *blocking* a tool unless a server-mediated check passes is Enforcement.
- **A CLI tool the agent is told it can run** (a command-line tool installed on the machine and named to the agent as a preferred way to do something). What it is: an executable the agent may shell out to, surfacing a deterministic capability the agent chooses to invoke. Best answers: a recurring pattern where the agent does by hand, badly, something a tool does reliably (hand-rolling a query a CLI answers, eyeballing something a linter would catch, manual steps a script automates). Enacted: install the CLI and add a standing-instruction line naming it and when to prefer it; possibly wrap it in a skill or command. Regimen: points / user builds. Boundary note: a CLI the agent *may* run is Guidance; a CLI run *in place of the model* as a non-negotiable step is Enforcement (deterministic automation).
- **A retrieval or knowledge source the agent can reach** (a docs site the agent is told to consult, an indexed knowledge base, a search tool, a "read the docs first" source). What it is: an authoritative source the agent is asked to consult before acting. Best answers: a recurring "wrong approach" or drift pattern rooted in the agent acting on memory instead of current truth (API drift, outdated patterns, version-specific behavior). Enacted: name the source in a standing instruction or a skill ("read the official docs before X"), or wire it as an MCP/CLI capability. Regimen: points / user builds.

## Group D: Process and selection choices (advisory decisions about how work is run)

These are not artifacts at all; they are durable *decisions about process* that the engineer adopts and may express to the agent as guidance. They belong in the taxonomy because the mental model is explicit that the kit is per-model and per-harness and that process is the lever, so a process choice is a legitimate Guidance move even when nothing is installed.

- **Harness or model selection as a process choice** (deciding to route a given intent of work to a particular harness or model). What it is: a routing decision, run on Feedback evidence, that a class of work goes to the harness or model that handles it best. Best answers: a recurring pattern where one intent of work consistently goes worse on the current harness or model (per-harness, per-model Outcome differences Feedback can show). Enacted: adopt the routing as a habit, optionally encoded as a routing note in an instruction file or a delegation skill; the move is a decision, not a file. Regimen: points (Feedback supplies the evidence; the choice is the engineer's). Boundary note: choosing a harness is Guidance; a gate that *forbids* a tool on a given harness is Enforcement.
- **Output-style or response-mode guidance** (asking the agent to adopt a concision level, a format, a tone, a structured-response habit). What it is: a standing preference about the shape of the agent's output. Best answers: a recurring "expressed dissatisfaction" pattern about how the agent communicates (too verbose, wrong format, missing structure) rather than what it does. Enacted: a standing-instruction line, an output-style config the harness supports, or a command that sets the mode. Regimen: points / user builds.
- **Scoping and decomposition habits** (a durable practice of breaking work down, bounding scope, sequencing, or framing the ask before handing it over). What it is: a process discipline about how work is framed and sized, expressed to the agent as a method to follow. Best answers: a recurring scope-drift or "misunderstood goal" pattern where work was handed over too big or too vague. Enacted: encode the habit as a skill or a kickoff template, or as a standing instruction ("plan before building"); the move can be pure practice. Regimen: points / user builds.

## What stays excluded (the Enforcement side, noted at the boundary)

These adjacent forms are excluded because they remove the model's choice; they are named here so the helper can recognize a misfit and hand off. A hook or gate that blocks an action; a permission or tool boundary that denies a capability; a CI or pre-merge check that fails the build; a sandbox that walls off the environment; schema-constrained output the harness will not emit unless valid; deterministic automation that runs in place of the model. Each has a Guidance shadow in the taxonomy above (the advisory version of the same surface), and the natural escalation in the canonical instances is exactly this crossing: ask first (Guidance), and when asking does not stick, remove the choice (Enforcement). The helper is guidance-side, so when a pattern's correction cost shows that asking has already failed repeatedly, the right answer is to hand off to the Enforcement side rather than to author a weaker advisory move.

# Part 2: The respond-step helper skill (high-level design)

## Purpose

Given a Feedback pattern the engineer has just seen (a recurring problem, with its intent-plus-outcome read and its correction cost), help the agent reach for the single right Guidance move from the full breadth of forms and enact it, while recognizing when the honest answer is Enforcement and handing off.

## Inputs the skill works from

The skill is invoked in conversation right after a pattern has been surfaced, so its primary inputs come from that surfacing and the live context, not from a fresh query it must run:

- **The surfaced pattern**: the recurring problem in plain language (what keeps happening), as named by Feedback or by the engineer.
- **The intent-plus-outcome read and the correction cost**: which intent of work this bites (refactor, bug-fix, feature, and so on) and where it lands on the Outcome ordinal, plus how much steering it took. The correction cost is load-bearing: it tells the helper whether asking has been tried and has failed (a strong cue toward Enforcement) or whether this is a first, cheap advisory move.
- **The harness and the model in play**: Guidance is per-harness and per-model, so the helper must know which CLI and which model the engineer is running, to pick a form that exists on that harness (the instruction-file name, the skills location, whether slash commands or subagents are supported) and to weigh whether the problem is harness-specific or universal.
- **The current work context**: the repo and the body of work (the `cwd` anchor), so the helper can choose project-scope versus global-scope and reach for project-local files (a `CONTEXT.md`, the project instruction file) versus the global ones.
- **Optionally, the underlying evidence**: the deterministic anchors behind the pattern (the churn, the tool thrash, the gate denials, the repeated edits), available via `regimen evidence` when the helper needs to confirm the pattern is real and recurring before recommending a durable, cost-bearing move.

## Core flow

The flow goes from "here is a recurring pattern" to "here is the specific move and how to enact it," and it spans the whole breadth of Part 1, not just find-or-build-a-skill.

1. **Read the pattern as a need, not a form.** Restate the surfaced pattern in terms of what recurring behavior must change and what the correction cost says about how hard asking has been. Do not jump to a form yet.
2. **Run the mechanism check first.** If the correction cost shows asking has already been tried and has not stuck (the canonical escalation: the model kept doing it after being told not to), or if the need is inherently "this must never happen" rather than "the agent should prefer," recognize that the honest answer is Enforcement, and hand off (see boundaries). Guidance moves are for needs where asking can plausibly work.
3. **Classify the need to a group, then a form.** Map the need onto the Part 1 groups by where the advice should live and how the agent should encounter it: an always-relevant small rule points at Group A (standing context); a heavy or situational procedure points at Group B (an invokable unit); a missing capability or stale-information problem points at Group C (a reachable tool or source); a routing or framing problem points at Group D (a process choice). Use the harness and model context to confirm the form exists on this harness. When several forms fit, prefer the cheapest durable one that the Feedback pattern can later validate (a one-line standing instruction before a whole new skill, a skill before a subagent), since beat 3 has to be able to tell whether the move worked.
4. **Decide find versus build versus reach-for** within the chosen form (the branches below), and produce the concrete enactment steps.
5. **Name the validation path.** Close by telling the engineer how to confirm the move earned its keep: re-run the same Feedback read (the see beat) after the move has had a chance to act, watching the same intent-plus-outcome and correction cost. A move that does not move the pattern is dead weight to revisit.

The decision among forms is the heart of the skill, and it is explicit branching, not a default to skills. Worked tells: a tool-preference miss with low correction cost resolves to a standing-instruction line (Group A), not a skill. A multi-step discipline the agent keeps skipping resolves to finding or authoring a skill (Group B). Stale-information drift resolves to making a docs source or MCP server reachable (Group C). One intent of work consistently going worse on this harness resolves to a routing decision (Group D). A "prefer X but it must hold" need where asking has already failed resolves to a hand-off to Enforcement.

## Outputs

The engineer or agent ends with three things, always together:

- **A recommended move**: the single chosen Guidance form, named concretely (this standing-instruction line, this skill to find or author, this MCP server to install, this routing decision), with a one-line reason tying it back to the pattern and why this form over the alternatives.
- **The enactment steps**: the concrete actions to put the move in place (which file to edit and the scope, the command to find or install, the skill scaffold to author, the config line to add), specific to the harness in play.
- **A pointer to validate via Feedback later**: the explicit beat-3 instruction to re-run the same Feedback read after the move has acted, so the loop closes and an unvalidated lever does not become silent dead weight.

## The find / build / reach-for branches

Once a form is chosen, the move is enacted by one of three branches, and the helper names which and how:

- **Find** (the move already exists somewhere; locate and install it). Used most for the skill form (commands and subagents either route through the same CLI when packaged as skills, or degrade to build). Enacted (resolved in the 2026-06-25 grill): the helper shells the Vercel `skills` CLI directly, `npx skills find <keywords>`, as a plain Bash command. It does NOT tap any harness-native skill-finder (that would not port across harnesses). The CLI's non-interactive direct-search mode is built for coding agents: it prints `owner/repo@skill`, install count, and a skills.sh URL per hit, plus the literal `npx skills add <owner/repo@skill>` install line. The query is the model distilling the surfaced pattern's NEED into keywords. The CLI is a SOFT dependency: if npx/node is present it works (npx fetches the CLI transiently), and if it is absent or the search returns nothing the helper falls straight to build (which is always the third presented option anyway, so there is no separate empty-result branch). Evaluation: for the shortlist the helper fetches each candidate's `SKILL.md` frontmatter / skills.sh page to read the description, judging two things together, does it answer THIS pattern's need, and does it lean on harness-specific tools or slash conventions that will not port to the harness in play; a full-body read happens only if the engineer wants to inspect before installing. Presentation: the helper always offers up to three options and installs nothing until the engineer picks, the top found candidate (name, `owner/repo@skill`, install count, a one-line why-it-matches, and the exact `npx skills add ...` command), the second found candidate in the same shape, and "build one specific to your need" as a permanent first-class third option. Install scope defaults to global (a discipline skill is usually cross-repo), dropping to project scope only when the pattern is clearly repo-specific; the CLI handles per-harness agent detection. It does not silently install, and it glances at what is already active (Feedback's `skillUsage`, or `npx skills list`) so it does not recommend installing something already present.
- **Build** (no good existing move; author one with the LLM). Used when the discipline is specific to this engineer, this repo, or this pattern. Enacted: author the artifact with the LLM in the form's shape (a `SKILL.md` with frontmatter and a procedure, a subagent definition, a command, a checklist, a `CONTEXT.md` section), grounded in the surfaced pattern and the evidence anchors, then place it where the harness discovers it. The helper drafts and proposes; the engineer owns the authoring decision.
- **Reach-for** (the move is a capability or a config edit, not an authored artifact). Used for MCP servers, CLI tools, retrieval sources, standing-instruction lines, memory edits, output-style settings, and routing decisions. Enacted: name the specific server / tool / source / config line / file edit, give the exact install-or-edit step and the scope, and (for capabilities) add the standing-instruction line that tells the agent when to prefer it. The helper points; the engineer or agent performs the edit.

Across all three branches, "Regimen points, does not supply" holds: the helper locates, drafts, or names the move, and it never ships a catalog of moves or installs lever content as if it were Regimen's product.

## Boundaries

- **When the honest answer is Enforcement, hand off.** The helper is guidance-side. When the correction cost shows asking has already failed repeatedly, or the need is "this must never happen" rather than "the agent should prefer," the helper says so plainly, names that this calls for a deterministic mechanism (a gate, a permission boundary, a CI check, schema-constrained output), and points to the Enforcement side rather than authoring a weaker advisory move that the same pattern already proved the model will ignore. This is the canonical escalation made operational (ask first; when asking does not stick, remove the choice).
- **On-demand and agent-mediated, never Clippy.** The helper activates only when the engineer has just seen a pattern and asks what to do about it; it never volunteers a move unprompted mid-conversation. The trigger is always the engineer's, even though the answer can surprise them. It proposes and enacts on request; it does not nag.
- **Points, does not supply.** The helper helps locate or author the engineer's own move; it carries no built-in catalog of skills, gates, or moves. Even the reference examples it might name (a reference gate as a starter) are starters, not a fixed menu. The content of the move is always the engineer's; Regimen supplies only the operator skill that helps reach for it.
- **Stay on the mechanism line.** The helper holds the advisory-versus-deterministic cut when classifying, and it does not relabel an Enforcement need as Guidance to keep the move on its own side.

## How it mirrors the operator-skill shape

The respond-step helper is built to be recognizably the same species as `feedback-evidence` and `feedback-judgment`, and installed the same way:

- **Same frontmatter and structure.** A `SKILL.md` with `name` and a `description` whose body states what it does and a precise activation trigger ("use right after Feedback surfaces a recurring pattern and the engineer asks what to do about it"), then a `# Title`, an intro that frames the move, a `## Process` of numbered steps, an outcome-handling step, and a `## Notes` section, matching the two Feedback skills line for line in shape.
- **Same install mechanism, its own package home.** Per the parallel-package decision it lives in `packages/guidance`, the Guidance lever's own operator skill (with an Enforcement sibling beside it), not a third skill under `packages/feedback`. It still mirrors the Feedback skills' shape and installs to `<configHome>/<skillsSubdir>/<name>/SKILL.md` through the same hooks-and-skills planner. How a guidance-package skill registers for bundling (a shared bundler, or a `guidanceInstall` that composes into the one `regimen install`) is a call for the guidance package architect-deep. It carries no `feedback-` prefix; it is named for the act beat.
- **Same harness-agnostic posture.** Like the Feedback skills, every step that touches a harness-specific fact (the instruction-file name, the skills location, whether subagents or slash commands exist) is resolved from the harness contract or detected, never hardcoded, so the one skill holds for every harness. The harness- and model-specificity of the *content* it recommends is a property of the move it points at, not of the operator skill itself.
- **Same operator-not-lever identity.** It operates Regimen's loop (it drives beat 2); it does not embody an engineering discipline. It only ever helps the engineer reach for their own discipline, which is why it is Regimen's own bundled artifact and still honors "points, does not supply."

# Decisions (resolved this session)

These were the open questions; here is where they landed.

- **Package home and count.** Each lever ships its own act-beat operator skill in its own package: the Guidance respond-helper in `packages/guidance`, with an Enforcement sibling beside it. The principle is agreed; the official sign-off and the exact package shape are folded into the enforcement-architecture revisit (below), but the leaning is firm. It is not a third `feedback-` skill under `packages/feedback`.
- **Enforcement hand-off, not enactment.** When the correction cost shows asking has already failed, the helper names the Enforcement need plainly and hands off. It does not enact the gate. The gate enactment belongs to the Enforcement-side act-beat helper, so each lever's operator stays on its own side.
- **Propose, do not auto-apply.** The helper drafts the move and the enactment steps and proposes them. It acts (installs a found skill, performs an edit) only on the engineer's explicit confirmation. On-demand, never Clippy.
- **No persistence in v1.** The recommendation stays ephemeral for now. Recording "this pattern led to this move, and validation showed whether it worked" is the not-yet-built over-time respond synthesis. It is safe to add later without breaking points-not-supplies, because storing the engineer's own decision about their own work is observability about the loop, not Regimen shipping a catalog of moves. Out of scope for v1.
- **No `feedback-` prefix.** The prefix signals the see beat and would mislabel an act-beat skill. It is named for the act beat and its package.

# Resolved in the 2026-06-25 find-branch grill

- **How does it know the harness and model in play?** RESOLVED: it reuses the Feedback skills' `cwd`-resolution plus harness detection (no new mechanism). The harness- and model-specificity of the move it recommends is a property of the move, not of the operator skill.
- **Where does the find branch actually search, and is that wired or named?** RESOLVED: the helper shells `npx skills find <keywords>` directly via Bash (the agnostic mechanism), not via any harness-native skill-finder. The CLI is a SOFT dependency with a build fallback (npx fetches it transiently when node is present; absent npx, no network, or zero results all collapse to the always-present "build" option). The full find / evaluate / present mechanics are folded into the "Find" branch bullet above.
- **One framing correction this grill surfaced (action item for the build):** the privacy claim must be re-derived. Drop the "everything local / one egress" wording in `docs/mental-model.md` (and any echo in the README and skills). The real claim is that captured conversation TELEMETRY never leaves the machine (Regimen does not exfiltrate what it observes); it must NOT imply zero network, since the instrumented harness itself egresses to a model provider and the find-branch makes an on-demand search call, both normal and expected.
