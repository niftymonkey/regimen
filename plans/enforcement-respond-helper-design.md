# Enforcement respond-step helper: mechanisms taxonomy and skill design

> Design doc for the Enforcement-side act-beat operator skill, the deterministic sibling of the Guidance respond-helper (`plans/guidance-respond-helper-design.md`). It is the same species of artifact as the two bundled Feedback skills (`feedback-evidence`, `feedback-judgment`) and the Guidance respond-helper: Regimen's own infrastructure, bundled and installed by Regimen, that lets the agent drive Regimen's loop in conversation. This one serves beat 2 (act) on the Enforcement side: it takes a Feedback pattern where asking has already failed and the honest move is to remove the model's choice, and it authors and wires the deterministic mechanism that does so. Part 1 enumerates the full breadth of Enforcement mechanisms (the design input). Part 2 designs the skill at a high level. The final section works out what `packages/enforcement` becomes given this design plus the two prior re-eval reports. Grounded in `docs/mental-model.md` section 5, ADR-0013, ADR-0002, ADR-0012, the PRD, `DOMAIN-LANGUAGE.md`, the two enforcement re-evals (`plans/enforcement-package-reeval.md`, `plans/enforcement-package-reeval-ponytail.md`), and the actual `packages/enforcement` source. Read-only investigation, no code changed.

## Framing carried in (locked, not relitigated)

Feedback is the center; Guidance and Enforcement are the two response levers acted with in beat 2 of the see / act / validate loop. The cut between the levers is mechanism, not form: Guidance is any advisory offering the agent is *asked* to use and may ignore; Enforcement is any deterministic mechanism that *removes* the choice, so the work cannot proceed until the mechanism is satisfied. Regimen points at lever content, it never supplies it: the respond-helper helps the user author and wire their own deterministic mechanism, and it ships no catalog of mechanisms. An operator skill operates Regimen's own loop; it is not lever content. This helper is the operator skill for the Enforcement act, exactly as the two Feedback skills are the operator skills for the see beat and the Guidance respond-helper is the operator skill for the Guidance act, and it mirrors their shape and install path. The earlier premise (that a denial is a discrete real-time act with no transcript footprint, so a fired mechanism must EMIT a `gate.denial` into Feedback's store) was empirically falsified: a gate denial lands in the captured transcript as an `is_error` tool-result carrying the deny reason, and Feedback's readers already project it to a judge-visible chunk on every harness. The Guidance respond-helper hands such cases off TO this helper rather than authoring a weaker advisory move the pattern already proved the model will ignore.

# Part 1: The taxonomy of Enforcement mechanisms

An Enforcement mechanism is anything the engineer puts between the agent and the work such that the agent *cannot* proceed in the disallowed way, regardless of what the model decides. The taxonomy below groups mechanisms by *where in the work the determinism is applied* (at the agent's tool boundary, at the environment boundary, at the output boundary, at the integration boundary, in the build pipeline, or by substituting a deterministic process for the model's). Each entry gives: what it is; the recurring Feedback pattern (and correction-cost signal) it best answers; how it is enacted (the concrete action: author the body, wire it into the harness hooks file, add a permission rule, add a CI check, configure a sandbox, constrain the output schema); whether it can EMIT a Feedback event when it fires (the `gate.denial` analog) or is silent; and whether Regimen ships it, points at it, or the user builds it. Across the whole taxonomy the ship-versus-author lean (worked out in the package-architecture section) is author-on-demand: Regimen ships only its own operator skills and the emit/wire seams, never a catalog of mechanism bodies, so "ships" never appears below for a mechanism itself. The helper AUTHORS the mechanism on demand; for the ones that fire, it WIRES emit so the denial lands as Feedback evidence.

## The mechanism boundary (read before the mechanisms)

Everything below is on the deterministic side: the model cannot choose its way past it and have the work still proceed. The boundary is drawn by mechanism, so the same surface can appear on either lever depending on how it is wired (the Guidance taxonomy names the advisory shadow of each mechanism below). A `CLAUDE.md` line that says "prefer pnpm" is Guidance; a pre-commit hook that rejects a commit using npm is Enforcement. An MCP server the agent *may* call is Guidance; a permission gate that *blocks* a tool unless a condition holds is Enforcement. An output-style preference is Guidance; a schema-constrained output the harness will not emit unless it validates is Enforcement. A CLI the agent *may* run is Guidance; a CI check that fails the build is Enforcement. The recurring tell: if a sufficiently determined or distracted model can ignore the artifact and the work still proceeds, it is Guidance, and it belongs in the Guidance taxonomy, not here. The honest exclusions, noted at each boundary below, are the cases where a surface *looks* deterministic but is actually advisory (a hook that only warns, a check the agent can skip, a "blocking" rule with an easy override the agent controls): those are Guidance and trigger the REVERSE handoff in Part 2.

One determinism caveat carried in from the live `rm-rf` gate (`examples/rm-rf-gate.ts:23-28`): a harness pre-tool hook is a guardrail, not always a hard boundary. On some harnesses and some shell paths a denied command can still reach the shell (Codex's `unified_exec` path bypasses the PreToolUse hook on some builds; its dedicated `PermissionRequest` hook is the stronger surface). The taxonomy notes, per mechanism, where the determinism is strong (the build fails, the sandbox has no network) versus where it is strong-by-convention-but-bypassable (a pre-tool hook the harness mostly but not always routes through). The helper must pick the strongest mechanism the pattern actually needs and the harness actually supports, not reflexively the pre-tool gate.

## Group A: Agent tool-boundary mechanisms (deny or constrain a tool call before it runs)

These fire at the agent's own tool boundary, the pre-tool hook event the harness exposes (`PreToolUse` for Claude and Codex, `preToolUse` for Copilot, `BeforeTool` for Gemini, per `GATE_PROFILES` in `gate-hooks.ts:84-89`). They are the most visible and most-wired Enforcement mechanism, and the one the current package implements. They are the natural home for "the model keeps doing a specific bad action" patterns, because they intercept the exact action. They can EMIT, and the emit seam exists precisely for them.

- **A discipline gate (a PreToolUse hook that denies a tool call).** What it is: an authored body (a `bun` TypeScript script reading the harness payload on stdin) that inspects a pending tool call and writes the shared Claude/Codex deny shape (`hookSpecificOutput.permissionDecision: "deny"`, `rm-rf-gate.ts:96-106`), or `exit 2` with a reason on stderr for harnesses using that form. Best answers: a recurring pattern where the model performs a specific disallowed action after being told not to (the em-dash-in-markdown pattern, a forbidden `rm -rf`, an inline heredoc commit body), where correction cost shows asking failed repeatedly (`accomplished-with-correction` or worse, the same correction recurring). Enacted: author the gate body (the inspect-and-deny logic for *this* engineer's rule), wire it into the harness's pre-tool event via the existing planner (`planGateHooks`), and wire emit (spawn `emit-denial` on a hit). Emit: YES, this is the canonical `gate.denial` emitter. Determinism: strong-by-convention-but-bypassable on some harness shell paths (see the boundary caveat); the strongest available pre-tool surface for the harness should be chosen. Regimen: AUTHORS on demand (the rule body is the engineer's; the deny shape, the wiring, and the emit are Regimen's reusable seams).
- **A pre-tool gate that constrains rather than denies (a conditional allow).** What it is: the same hook surface, but instead of a flat deny it permits the call only when a deterministic precondition holds (a path is inside the repo, a command targets an allowed directory, a flag is present), denying otherwise. Best answers: a pattern where the action is fine in-bounds but the model keeps stepping out of bounds (writing outside the workspace, touching a protected path, running a command without a required guard flag). Enacted: author the precondition check in the gate body, wire and emit as above. Emit: YES (a denial when the precondition fails is a `gate.denial`). Determinism: same as the deny gate. Regimen: AUTHORS on demand. Boundary note: a hook that only *warns* when the precondition fails but lets the call through is Guidance (advisory), not this; the helper must wire a real deny.
- **A tool-disablement boundary (remove a tool from the agent's available set).** What it is: a harness-level configuration that takes a whole tool or tool family out of the agent's reach for a session or a project, so it is never offered, not merely denied per-call. Best answers: a pattern where an entire capability is the problem and there is no good in-bounds use (the agent should never run web fetches in this repo, should never use a destructive bulk-edit tool), distinct from the per-call gate which allows the tool conditionally. Enacted: edit the harness's tool-availability config (where the harness supports it), not the hooks file. Emit: typically SILENT (a tool that is never offered produces no denial event; some harnesses can be configured to log an attempt, but the default is no footprint). Determinism: strong (the tool is absent). Regimen: AUTHORS/points the config edit on demand. Boundary note: telling the agent "don't use tool X" in `CLAUDE.md` is the Guidance shadow; removing X from the toolset is this.

## Group B: Permission and capability-boundary mechanisms (deny a capability at the harness or OS layer)

These deny a *capability* rather than inspecting a specific call: a permission rule in the harness's own allow/deny config, or an OS-level credential or capability the agent simply does not have. They differ from Group A in that the determinism comes from a static rule or an absent grant, not from an authored inspect-and-decide body.

- **A harness permission rule (allow/deny/ask entries in the harness's permission config).** What it is: a declarative rule in the harness's own permission system (the allow-list / deny-list / ask-list the harness consults before running a tool), e.g. a deny entry for a Bash command pattern or a write path. Best answers: a recurring pattern that a static rule can express without custom inspection logic (a fixed command prefix that must never run, a directory that must never be written), where the model kept doing it and a per-call authored gate would be overkill. Enacted: add the permission rule to the harness's permission config file (the format is per-harness; the helper resolves which file and which rule shape from the harness in play). Emit: usually SILENT by default (a harness permission denial is internal to the harness and does not flow through Regimen's emit seam), unless the harness exposes a permission-decision hook that can be wired to emit (the stronger Codex `PermissionRequest` surface is the analog). Determinism: strong (the harness will not run the call). Regimen: AUTHORS/points the rule on demand. Boundary note: a permission *ask* entry (prompt-the-user) is a softer boundary; if the agent or an auto-approve setting can clear the prompt, it drifts toward advisory, and the helper should prefer a hard deny when the pattern proves asking failed.
- **A credential or capability denial at the OS layer.** What it is: not granting the agent (or the shell it runs in) a credential, a network route, or a filesystem permission, so an action is impossible rather than merely disallowed (no write bit on a directory, no token in the environment, no route to a host). Best answers: a pattern where the safest move is that the capability simply does not exist for the agent's process (the agent keeps trying to reach a forbidden network endpoint, keeps trying to write a read-only tree). Enacted: configure the OS-level permission, env, or network scope for the process the harness runs in (this shades into Group C sandboxing when the scoping is comprehensive). Emit: SILENT (an OS-level failure surfaces as a tool error in the transcript, which Feedback's capture already records, not as a discrete `gate.denial`). Determinism: strong (the OS enforces it). Regimen: points the user to the OS-level change on demand; this is the one group where "user builds in their environment" dominates, because it is outside any harness or repo file Regimen can author.

## Group C: Environment-boundary mechanisms (wall off the environment the agent runs in)

These wall off the *environment* so disallowed effects cannot escape, independent of any specific call. They are the heaviest determinism (the model cannot reach what is not there) and the most silent (a walled-off effect leaves a tool error, not a denial event).

- **A sandbox the agent runs inside (a container, a VM, a restricted profile, a network-isolated shell).** What it is: the whole agent session runs in a confined environment with no path to the disallowed effect (no network egress, no access outside a mounted workspace, no privileged syscalls). Best answers: a pattern where the *category* of risk is broad and per-call gating is whack-a-mole (the agent keeps finding new ways to reach the network, keeps touching files outside the project, and enumerating each is hopeless), where the honest move is to remove the whole class of capability. Enacted: configure the sandbox the harness runs in (a devcontainer, a restricted shell, a network policy); this is a process/environment setup, not a repo file the planner wires. Emit: SILENT (the sandbox produces tool failures captured in the transcript, not discrete denial events). Determinism: strongest in the taxonomy (the capability is physically absent). Regimen: points the user to the sandbox configuration on demand; like the OS layer, the body lives outside any file Regimen authors.
- **A workspace or filesystem jail (scope the agent's reachable filesystem).** What it is: a narrower form of sandbox, confining the agent's reads and writes to a subtree. Best answers: a recurring out-of-bounds-write pattern that a per-call path gate (Group A) could also address, chosen here when the engineer wants the boundary at the environment rather than maintaining inspection logic. Enacted: configure the workspace root / chroot / mount scope for the agent's process. Emit: SILENT. Determinism: strong. Regimen: points on demand. Boundary note: the Group A conditional-allow gate is the in-repo, emit-capable alternative to this; the helper chooses between them on whether the engineer wants a denial event (pick the gate) or a hard environmental wall with no per-call logic (pick the jail).

## Group D: Output-boundary mechanisms (constrain the shape of what the model emits)

These make the model's *output* conform deterministically, so a malformed or off-spec output cannot be emitted at all. The determinism is in the harness's or the tool's output contract, not in a hook over a tool call.

- **Schema-constrained output (structured-output / tool-call schema the harness enforces).** What it is: the harness (or the API beneath it) is configured so the model's output must validate against a schema before it is accepted (a JSON schema on a tool call, a structured-output mode, a grammar-constrained decode). Best answers: a recurring pattern where the model produces structurally-wrong output that then has to be corrected (free-text where a strict shape was needed, missing required fields, invalid enums), and asking for the shape did not hold. Enacted: configure the schema on the tool definition or the structured-output setting the harness exposes; author the schema (the field shape is the engineer's; the wiring is Regimen-pointable). Emit: SILENT by default (a schema rejection is handled inside the harness/provider loop and surfaces as a retry or an error in the transcript, not as a `gate.denial`); a wrapper that intercepts and records rejections is possible but not the default. Determinism: strong (the harness will not emit non-validating output). Regimen: AUTHORS the schema / points the config on demand. Boundary note: "please always return JSON shaped like X" in an instruction file is the Guidance shadow; a schema the harness enforces is this.
- **A formatting or content gate on written output (deterministic post-generation rejection of a file write).** What it is: a pre-write hook (Group A surface) specialized to the *content* the model is about to write rather than the command (the em-dash gate is exactly this: it scans `tool_input.content` / `new_string` and denies on a hit, `em-dash-gate.sh:23-30`). Best answers: a recurring content-quality pattern in written artifacts (the forbidden character, a banned phrase, a required header missing), where the model kept emitting it after being told not to. Enacted: author the content-scan gate body, wire and emit as Group A. Emit: YES (it is a pre-tool gate; it emits a `gate.denial`). Determinism: strong-by-convention (it is a pre-write hook). Regimen: AUTHORS on demand. Note: this is the bridge case showing schema-vs-hook is a choice of *where* the output contract lives (in the harness's decode, Group D schema; or in a post-hoc content scan, this entry).

## Group E: Integration and pipeline mechanisms (fail the work downstream of the agent)

These let the agent produce whatever it produces, then deterministically reject the result at an integration boundary the agent cannot clear on its own. The determinism is that the *work does not land* (the build fails, the merge is blocked) unless the check passes, and the agent cannot self-approve.

- **A CI check / required status check (fail the build on a rule).** What it is: a pipeline step (lint, type-check, test, a custom rule) wired as a required check so a violating change cannot merge. Best answers: a recurring pattern where the model's output is wrong in a way a deterministic check catches (a lint rule it keeps violating, a test it keeps breaking, a type error it keeps introducing), and in-conversation asking did not hold across sessions. Enacted: add or extend the CI config (the check command and its required-status wiring); author the rule the check runs. Emit: SILENT to Regimen by default (a CI failure is a pipeline event, not an in-session `gate.denial`; it leaves its trace in the build, not the conversation); a bridge that records a CI rejection back into the store is conceivable but out of the in-session loop. Determinism: strong (the merge is blocked by the host's required-check enforcement, which the agent cannot override). Regimen: AUTHORS the check / points the config on demand.
- **A pre-merge / branch-protection gate (block the merge itself).** What it is: the host-level rule that a branch cannot be merged unless conditions hold (required reviews, required checks, a protected branch). Best answers: a pattern where the failure mode is *landing* unreviewed or unvalidated work, not the content per se (the agent merged something it should not have, pushed straight to main), where the honest fix is that the path to land is closed. Enacted: configure branch protection / merge rules at the host. Emit: SILENT (host-level, off the in-session loop). Determinism: strong. Regimen: points the user to the host config on demand.
- **A pre-commit / pre-push hook (deterministic local gate before the commit lands).** What it is: a git hook (or the harness-run equivalent) that rejects a commit or push that violates a rule, locally, before it leaves the machine. Best answers: a recurring pattern caught best at commit time (a secret about to be committed, a formatting rule, a forbidden file), where asking the agent to check first did not hold. Enacted: install/extend the git hook (e.g. via the existing pre-commit setup), author the rule. Emit: SILENT by default to Regimen, though a pre-commit hook *could* be wired to emit a denial across the same seam (it runs locally, so it has access to the buffer); whether that is worth it is a design choice, not a default. Determinism: strong locally (the commit is rejected), but a determined agent can pass `--no-verify`, so a pre-commit hook is strong-by-convention unless paired with a server-side check (the CI/branch-protection entries close that gap). Regimen: AUTHORS/points on demand.

## Group F: Deterministic substitution (run a deterministic process in place of the model's judgment)

This is the mechanism with no advisory shadow at the call site: instead of letting the model do a thing and gating it, a deterministic process *does the thing*, removing the model's discretion entirely.

- **Deterministic automation in place of the model (a script/codemod/formatter runs the step, the model does not).** What it is: a non-negotiable deterministic step that replaces a model decision (a formatter that rewrites every file on save, a codemod that performs a migration, a generator that produces the artifact), so the model never had the choice to do it differently. Best answers: a recurring pattern where the model does, inconsistently, something a deterministic tool does reliably (hand-formatting that drifts, a repetitive transform it gets subtly wrong each time, a generated file it keeps hand-editing). Enacted: wire the deterministic step into the workflow so it always runs (a format-on-write hook, a build step, a generation step), authored or pointed-at. Emit: SILENT (a substitution leaves no denial; its effect is that the artifact is correct, visible in the conversation Feedback already records). Determinism: strong (the model's version never exists). Regimen: AUTHORS/points on demand. Boundary note: a CLI the agent *may* run is the Guidance shadow; a step that runs *in place of* the model as a non-negotiable part of the workflow is this.

## What stays excluded (the Guidance side, noted at the boundary)

These adjacent forms are excluded because the model can still choose to ignore them and the work proceeds; they are the advisory shadow of the mechanisms above, and they live in the Guidance taxonomy. A standing-instruction line ("never use an em-dash"); a skill or a checklist the agent is asked to follow; an MCP server or CLI the agent *may* call; a "read the docs first" source; an output-style preference; a routing decision. Each has an Enforcement counterpart above (the deterministic version of the same surface), and the natural escalation is exactly the crossing: ask first (Guidance), and when asking does not stick, remove the choice (Enforcement). This helper is enforcement-side, so when a pattern arrives where asking has NOT yet been tried (low correction cost, a first cheap advisory move would plausibly work), the right answer is the REVERSE handoff back to Guidance rather than over-reaching to a gate the pattern does not yet justify (see Part 2 boundaries).

# Part 2: The respond-step helper skill (high-level design)

## Purpose

Given a Feedback pattern where asking has already failed (a recurring problem with high correction cost, where the model kept doing it after being told not to), help the agent author and wire the single right deterministic mechanism from the full breadth of Part 1, hooking up emit where the mechanism fires, so the model's choice is removed and the denial lands as Feedback evidence the validate beat can read.

## Inputs the skill works from

The skill is invoked in conversation right after the Guidance respond-helper (or the engineer) has determined that asking failed and the honest move is to remove the choice, so its primary inputs come from that hand-off and the live context, not from a fresh query it must run:

- **The surfaced pattern**: the recurring problem in plain language (what specific action or output keeps happening), as named by Feedback or carried in from the Guidance hand-off.
- **The intent-plus-outcome read and the correction cost that proves asking failed**: which intent of work this bites and where it lands on the Outcome ordinal, and critically the correction-cost history showing asking was tried and did not stick (the model corrected the same way repeatedly, `accomplished-with-correction` recurring on the same pattern). This is load-bearing in the opposite direction from the Guidance helper: there, low correction cost favored a cheap advisory move; here, a *failed* advisory history is the precondition for acting at all, and its absence triggers the reverse handoff.
- **The harness and the model in play**: the wiring target is per-harness. The helper must know which CLI and model the engineer runs to pick a mechanism the harness supports (the pre-tool event name from `GATE_PROFILES`, whether the harness exposes a permission config, a tool-disablement setting, a structured-output mode, a stronger permission-decision hook) and to choose the strongest available surface (e.g. Codex's `PermissionRequest` over `PreToolUse` where it matters).
- **The current work context**: the repo and the body of work (the `cwd` anchor), so the helper chooses project-scope versus global-scope, reaches the right config home (Gemini's project-level divergence, ADR-0011), and decides whether the mechanism is repo-local (a CI check, a pre-commit hook) or harness-global (a user-level gate).
- **Optionally, the underlying evidence**: the deterministic anchors behind the pattern (the repeated edits, the prior `gate.denial` rows if an earlier weaker gate exists, the tool thrash), available via `regimen evidence`, when the helper needs to confirm the pattern is real and recurring before wiring a durable, cost-bearing mechanism.

## Core flow

The flow goes from "asking has failed on this pattern" to "here is the deterministic mechanism, authored and wired, emitting to Feedback," and it spans the whole breadth of Part 1, not just a PreToolUse gate.

1. **Read the pattern as a determinism need, not a gate.** Restate the surfaced pattern in terms of *what must become impossible* and *where in the work the determinism should sit* (at the tool call, at the environment, at the output, at the integration boundary, or as a substitution). Do not jump to a pre-tool gate by reflex.
2. **Run the reverse-handoff check first.** Confirm the precondition: has asking actually failed? If the correction cost does NOT show a tried-and-failed advisory history (this is a first occurrence, or no advisory move has been made yet, or the cost is low), hand BACK to Guidance rather than reaching for a deterministic mechanism the pattern does not yet justify (see boundaries). Enforcement mechanisms are for needs where asking has already proven insufficient or where the need is inherently "this must never happen."
3. **Classify the need to a group, then a mechanism.** Map the need onto the Part 1 groups by where the determinism sits: a specific bad *action* the model keeps taking points at Group A (a pre-tool gate) or Group B (a permission rule) depending on whether custom inspection is needed; a whole *capability* that should not exist points at Group B or Group C (tool disablement, sandbox, jail); a malformed *output* points at Group D (schema or content gate); a wrong result that should not *land* points at Group E (CI, pre-merge, pre-commit); a step the model does inconsistently that a tool does reliably points at Group F (substitution). Use the harness and model context to confirm the mechanism exists on this harness and to pick the strongest available surface. When several mechanisms fit, prefer the one that (a) emits a Feedback event if the pattern needs validating in the loop (Groups A and the content gate in D emit; the rest are silent), and (b) sits at the lightest boundary that actually closes the gap.
4. **Author, wire, and hook up emit** within the chosen mechanism (the branches below), and produce the concrete enactment steps. For the emit-capable mechanisms, wiring emit is not optional: a gate that denies but does not record leaves beat 3 blind to whether it is firing.
5. **Name the validation path.** Close by telling the engineer how to confirm the mechanism earned its keep: re-run the same Feedback read (the see beat) after the mechanism has had a chance to fire, watching two things together: the `gate.denials` now appearing in the store (the mechanism IS firing, for the emit-capable ones) AND the original pattern abating in the intent-plus-outcome read (the mechanism is *working*, not just firing). A mechanism that never fires may be mis-wired; one that fires constantly without the pattern abating may be mis-targeted; both are dead-weight signals to revisit.

The decision among mechanisms is the heart of the skill, and it is explicit branching, not a default to a PreToolUse gate. Worked tells: a forbidden character in written files resolves to a content gate (Group D content entry, which emits). A specific destructive command resolves to a pre-tool gate (Group A) or a harness permission deny (Group B) depending on whether the rule needs inspection logic. An entire capability that should never be used resolves to tool disablement (Group A) or a sandbox (Group C). Malformed structured output resolves to a schema (Group D). Work landing unreviewed resolves to a pre-merge gate (Group E). A transform the model gets subtly wrong every time resolves to deterministic substitution (Group F). A pattern where asking has NOT yet been tried resolves to a reverse handoff to Guidance.

## Outputs

The engineer or agent ends with four things, always together:

- **The recommended mechanism**: the single chosen Enforcement mechanism, named concretely (this pre-tool content gate, this harness permission deny, this tool disablement, this output schema, this CI check, this deterministic substitution), with a one-line reason tying it to the pattern, why this mechanism over the alternatives, and why this boundary (tool / environment / output / integration / substitution) is the right place for the determinism.
- **The enactment steps**: the concrete actions to put the mechanism in place, specific to the harness in play (the gate body to author and where it lands, the planner wiring into the pre-tool event, the permission rule and which config file, the schema and which setting, the CI config edit, the substitution step).
- **The emit wiring, where applicable**: for the emit-capable mechanisms (Group A gates, the Group D content gate), the wiring that makes a denial record a `gate.denial` across the store-write seam (spawn `emit-denial` on a hit, carrying the resolved harness via `REGIMEN_HARNESS`), so the deterministic act becomes Feedback evidence. For the silent mechanisms, an explicit note that this one will NOT show as a `gate.denial` and beat-3 validation must read the abating pattern (and the transcript-visible tool errors) instead.
- **A beat-3 validation pointer**: the explicit instruction to re-run the same Feedback read after the mechanism has had a chance to fire, watching the `gate.denials` appear AND the original pattern abate, so the loop closes and an unvalidated, cost-bearing mechanism does not become silent dead weight.

## The author / wire branches

Once a mechanism is chosen, it is enacted by authoring a body, wiring it into the harness, and (where it fires) wiring emit. The helper names which and how. Note the asymmetry from the Guidance helper: there, "find an existing one" was a first-class branch (skill collections hold reusable skills). Here, "find" is far weaker, because a deterministic mechanism is almost always the engineer's *specific* rule (this character, this command, this path, this schema), so the dominant branch is AUTHOR, and the ship-versus-author fork (below) lands on author-on-demand.

- **Author the mechanism body** (the rule itself). For a gate: a `bun` TypeScript body that reads the harness payload on stdin, applies the engineer's specific check, and writes the shared deny shape, authored Windows-safe in TypeScript so it runs under the one runtime Regimen already requires (no shell, no `jq`, no per-OS port). For a permission rule: the deny entry in the harness's permission config. For a schema: the field shape on the tool definition or structured-output setting. For a CI check: the rule the check runs. The helper drafts the body grounded in the surfaced pattern and the evidence anchors; the engineer owns the authoring decision and the approval.
- **Wire it into the harness** (put the authored body where it fires). For a gate: merge it onto the harness's pre-tool event via the existing planner (`planGateHooks`, which knows the per-harness event name and the Gemini name+matcher quirk from `GATE_PROFILES`), idempotently and marker-stamped so it never clobbers the capture leaf or the user's own hooks. For a permission rule: write it into the permission config file the harness reads. For a CI check: edit the CI config. For a sandbox / tool-disablement: edit the harness or environment config. The helper resolves which file and which shape from the harness in play; it never hardcodes one harness.
- **Wire emit for the ones that fire denials** (make the denial Feedback evidence). For the emit-capable mechanisms (Group A gates, the Group D content gate), wire the gate body to spawn `emit-denial` on a hit, carrying `REGIMEN_HARNESS` so the recorded denial is labelled correctly, across the published store-write seam so the gate never imports Feedback. For the silent mechanisms, there is no emit to wire; the helper says so and points validation at the abating pattern.

Across all branches, "Regimen points, does not supply" holds: the helper authors, drafts, or names *the engineer's own* mechanism, and it ships no catalog of mechanisms and installs no maintained gate bodies as if they were Regimen's product. The reusable seams Regimen DOES ship (the deny shape, the planner, the emit seam) are operator infrastructure, the way a denial becomes evidence, not lever content.

### The ship-versus-author fork, addressed head-on

The load-bearing fork is whether Regimen ships any example gates or maintained gate code at all, or whether the helper authors mechanisms on demand. This design takes the author-on-demand side, and the helper is the mechanism that makes it viable. The case:

- **Author-on-demand kills three problems at once.** It removes shipped-gate staleness (a reference gate drifts from the harness payload shapes it parses), it removes the maintenance burden (every shipped gate is code Regimen must keep working across four harnesses and three OSes), and it removes the shell-gate-versus-TypeScript Windows port entirely, because there is no shipped shell gate to port. The two prior re-evals both flag the shell gates plus the `win32` skip as the package's clearest Windows-first gap (`enforcement-package-reeval.md` section 5, `enforcement-package-reeval-ponytail.md` "out of scope but worth a note"); author-on-demand dissolves it rather than porting it.
- **The helper authors Windows-safe by construction.** Because the helper authors every gate as a `bun` TypeScript body (never a shell script), the authored gate runs under the one runtime Regimen requires on every OS. The forward-slash path discipline Feedback's capture already proved on native Windows (`capture-hooks.ts`, `.replaceAll("\\", "/")`) is applied to the authored gate's wired command. There is no `jq` dependency, no `bash` dependency, no `SHELL_GATES` preflight, and no per-OS divergence in the authored body.
- **What this leaves shippable.** Regimen still ships the *seams*: the store-write seam (`denial-store.ts` plus `emit-denial.ts`), the wiring planner (the per-harness pre-tool event knowledge in `GATE_PROFILES`), and the deny-shape convention. It does NOT ship `examples/*` gate bodies as product, nor the `GATE_COMMANDS` catalog of fixed gate ids. The one nuance: a single minimal reference gate may survive as a *test fixture and documentation exemplar* (the `rm-rf` gate is the fixture the emit integration test drives, `rm-rf-gate.ts:8-11`), but it is positioned as "the shape an authored gate takes," not as "a gate Regimen maintains for you to install." That keeps the integration test honest without re-introducing a catalog.

## Boundaries

- **The REVERSE handoff: when asking has not yet been tried, hand back to Guidance.** The helper is enforcement-side and deterministic mechanisms are not free (a gate is code to maintain, a sandbox changes the workflow, a CI check slows the pipeline). When the correction cost does NOT show a tried-and-failed advisory history, when this is a first occurrence, or when a cheap advisory move would plausibly work, the helper says so plainly and hands BACK to the Guidance respond-helper rather than over-reaching to a gate. This is the mirror of the Guidance helper's forward handoff, and together they make the canonical escalation operational in both directions: Guidance hands forward when asking has failed; Enforcement hands back when asking has not yet been tried. Over-reaching to a gate on a first occurrence is the failure mode this boundary prevents.
- **On-demand and agent-mediated, never Clippy.** The helper activates only when the engineer (or the Guidance hand-off) has established that asking failed and asks what deterministic move to make; it never volunteers a gate unprompted mid-conversation. The trigger is always the engineer's, even though the chosen mechanism can surprise them. It proposes and enacts on request; it does not nag and it does not auto-install a gate.
- **Points, does not supply.** The helper authors or names the engineer's OWN mechanism; it carries no built-in catalog of gates, no maintained gate bodies, no fixed menu of mechanisms. The only reusable things in play are Regimen's own operator seams (the emit seam, the planner, the deny shape), which are infrastructure for making a denial observable, not lever content. The content of the mechanism is always the engineer's.
- **Hold the mechanism line.** The helper holds the deterministic-versus-advisory cut when classifying, and it does not dress an advisory need as a gate to keep the move on its own side. A pattern that genuinely wants a softer touch (a preference, a first nudge) is a Guidance need; the helper hands it back rather than authoring a deterministic mechanism the pattern does not justify. Conversely, it does not author a "gate" that only warns (that is advisory wearing a gate's clothes); an Enforcement mechanism must actually remove the choice.
- **Propose, do not auto-apply.** The helper drafts the mechanism body, the wiring, and the emit and proposes them. It acts (writes the gate file, edits the config, wires the hook) only on the engineer's explicit confirmation, consistent with the Guidance helper.

## How it mirrors the operator-skill shape

The respond-step helper is built to be recognizably the same species as `feedback-evidence`, `feedback-judgment`, and the Guidance respond-helper, and installed the same way:

- **Same frontmatter and structure.** A `SKILL.md` with `name` and a `description` whose body states what it does and a precise activation trigger ("use right after a Feedback pattern shows asking has failed and the engineer, or the Guidance respond-helper, decides the honest move is to remove the model's choice"), then a `# Title`, an intro that frames the act, a `## Process` of numbered steps, an outcome/validation step, and a `## Notes` section, matching the two Feedback skills and the Guidance respond-helper line for line in shape.
- **Same install mechanism, the lever's own package home.** It lives in `packages/enforcement` as the Enforcement lever's own operator skill (the sibling of the Guidance respond-helper in `packages/guidance`), NOT a third skill under `packages/feedback`. It mirrors the Feedback skills' shape and installs to `<configHome>/<skillsSubdir>/<name>/SKILL.md` through the same hooks-and-skills planner. How an enforcement-package skill registers for bundling (a shared bundler, or an `enforcementInstall` that composes into the one `regimen install`) is a call for the enforcement package architect-deep below. It carries no `feedback-` prefix; it is named for the act beat on the Enforcement side.
- **Same harness-agnostic posture.** Like the Feedback skills, every step that touches a harness-specific fact (the pre-tool event name, the permission-config location and shape, whether a structured-output mode or a tool-disablement setting exists, the config home and Gemini's project-level divergence) is resolved from the harness contract or `GATE_PROFILES` or detected, never hardcoded, so the one skill holds for every harness. The harness- and model-specificity of the *mechanism* it authors is a property of the mechanism, not of the operator skill itself.
- **Same operator-not-lever identity.** It operates Regimen's loop (it drives beat 2 on the Enforcement side); it does not embody an engineering discipline. It only ever helps the engineer author and wire their own deterministic mechanism, which is why it is Regimen's own bundled artifact and still honors "points, does not supply."

# Implications for the enforcement package architecture

Given Part 1, this design, the author-on-demand lean, and the two prior re-evals, `packages/enforcement` stops being "a small catalog of reference gates plus the wiring to install them" and becomes "the operator skill that authors deterministic mechanisms on demand, sitting on the irreducible seams that make a denial observable and wireable." The package's center of gravity moves from shipped content to operator infrastructure. Concretely:

## What STAYS (the irreducible seams plus the operator skill)

- **The emit seam: GOES (reversed 2026-06-25, see DECISIONS).** `src/denial-store.ts` plus `hooks/emit-denial.ts` are DELETED. The earlier framing called this "the package's reason to exist," on the premise that a denial had no transcript footprint. That premise was empirically false (denials are captured), so the seam was a redundant second copy and Enforcement validates like Guidance instead. The package's reason to be a separate package is now its own act-beat operator skill plus the gate-wiring concern, not emit.
- **The wiring planner, with the shared-planner extraction.** The pure planner (`gate-hooks.ts`) is load-bearing in FUNCTION (the authored gate must be merged onto the right per-harness pre-tool event, idempotently, marker-stamped, without clobbering the capture leaf or user hooks) but is a ~300-line clone of Feedback's capture planner in FORM (`enforcement-package-reeval.md` section 3, finding 1). The recommendation stands and is reinforced by this design: extract one shared, role-parameterized hooks-file merge engine into `@regimen/shared`, with the planner types, `resolveHarnessHome`, the clone-root resolver, and `assertSafeClonePath` moving to shared too, so Enforcement's gate planner and Feedback's capture planner both become thin callers. This is the prerequisite that also makes `packages/guidance` cheap, because every lever that wires into a harness target reuses the same engine.
- **`GATE_PROFILES` (the per-harness pre-tool event facts).** The small data table mapping each harness to its pre-tool event name and the Gemini name+matcher quirk (`gate-hooks.ts:84-89`). Both re-evals keep it: it is data with four distinct rows the planner genuinely branches on, the analog of Feedback's capture descriptor. It stays (likely renamed to a small `profiles` data module). When the helper authors a gate, this is how the wiring knows where it fires per harness.
- **The deny-shape convention.** The shared Claude/Codex `hookSpecificOutput.permissionDecision: "deny"` shape (and the `exit 2` form) the authored gate writes. This is convention plus a tiny bit of reference code, the thing the helper's authored bodies conform to. It stays as the documented shape the helper authors against.
- **The operator skill itself.** The new respond-step helper `SKILL.md` lives here, in `packages/enforcement`, as the lever's own act-beat operator (sibling to the Guidance helper in `packages/guidance`). This is the package's new primary user-facing artifact: not gates it ships, but the skill that authors gates on demand.
- **The `install`/`uninstall` facade, slimmed.** The two symbols the unified CLI dispatches to (`packages/cli` imports only `install`/`uninstall`/`GateId`). They stay as the in-process entry, but their job shifts: with no shipped gate catalog, `install` is mostly "bundle the operator skill into the one `regimen install`" plus retaining the planner-based wiring path the helper uses when it authors a gate. The exact composition (does enforcement's install lay down the skill via a shared bundler, like the Feedback skills?) is the architect-deep call below.

## What GOES (the shipped content and the dead surface)

- **The `examples/*` gate bodies as shipped product.** `em-dash-gate.sh`, `inline-message-guard.sh`, and the `rm-rf-gate.ts` *as a shipped catalog* go: the helper authors these on demand instead. The em-dash and inline-message disciplines are exactly the kind of engineer-specific rule the helper should author Windows-safe in TypeScript rather than ship as maintained shell scripts. A single minimal reference gate (the `rm-rf` body) may survive ONLY as the emit integration test's fixture and a documentation exemplar of the authored shape, explicitly not as an installable catalog entry.
- **The `GATE_COMMANDS` catalog.** The fixed `GateId` union (`rm-rf | em-dash | inline-message`) and the command-builder table (`gate-commands.ts`) go: a fixed menu of three gate ids is exactly the catalog "points, does not supply" rules out, and author-on-demand replaces it. The command-building logic (interpolate the clone path, forward-slash for Windows, carry `REGIMEN_HARNESS`, validate the path) survives as a small helper the planner uses when wiring an *authored* gate, but the *catalog of ids* does not.
- **The shell-gate Windows port (avoided, not done).** Because the shell gates go and the helper authors only TypeScript bun gates, the `win32` skip in `install`/`uninstall` (`cli/index.ts:268-273,307-312`), the `SHELL_GATES` set, and the `warnIfShellGateMissingJq` preflight (`cli/index.ts:38,133-140`) all delete, and the `jq`/`bash` runtime dependencies disappear. The Windows gap the two re-evals flag is closed by removal, not by porting. The one carry-over discipline: the authored gate's wired command must forward-slash its path (the Feedback `capture-hooks.ts` pattern) so it survives a POSIX-style shell on native Windows.
- **The dead `wireGates`/`unwireGates` public surface.** Both re-evals rank this the biggest clean cut: ADR-0012 demoted the wiring verbs to internal steps, the unified CLI never imports them, and only `install`/`uninstall` call them. Fold them into `install`/`uninstall` as private helpers, drop the exports and the `WireGatesOptions`/`UnwireGatesOptions` interfaces, and drop the README's standalone `wire-gates` surface. With the catalog gone and the helper driving authored-gate wiring, the public wiring verbs have even less reason to exist.
- **The stale framing.** The `src/cli/` directory path (it is a facade, not a CLI), the README's standalone-install block, and the overlapping `cli.test.ts`/`cli-facade.test.ts` pair (one documenting a deleted subprocess path) all align to ADR-0012, per the re-evals. Lower priority than the content removal, but it comes along for free.

## Where the operator skill sits

The respond-step helper `SKILL.md` sits in `packages/enforcement`, beside the slimmed facade and the seams, as the lever's own act-beat operator. The package's shape after this is: the operator skill (the new primary artifact) + the emit seam + the wiring planner (now a thin caller of the shared engine) + `GATE_PROFILES` data + the deny-shape convention + the slimmed `install`/`uninstall` facade. That is a thin lever sitting on a shared install/contract spine, exactly the shape the parallel Guidance package takes, with one honest asymmetry the prior re-eval already named: Enforcement keeps the emit seam (a denial is a discrete act that must self-report) and Guidance has no emit analog (an advisory move leaves its trace only in the conversation Feedback already records). Designing the shared planner now, so the emit seam is the ONLY Enforcement-specific module left, is what makes that asymmetry clean rather than accidental.

# Open questions for the human (ALL RESOLVED 2026-06-25, see DECISIONS LOCKED near the top)

The bullets below are the questions as they stood before the grill; the DECISIONS LOCKED block at the top of this doc is the authoritative resolution for every one (drop emit, scope-coupled gate location, v1 wires pre-tool gates and points the rest, reference gate as a wiring fixture only, strongest-surface deferred, parallel-skill-per-lever signed off). Kept here for provenance.

- **Does the single reference gate survive as a test fixture, or does the emit integration test get a smaller synthetic fixture?** Author-on-demand argues for no shipped gate bodies, but the emit seam needs an integration test that drives a real gate end-to-end. Keep the minimal `rm-rf` body purely as that fixture (positioned as "the authored shape," not a catalog entry), or replace it with a synthetic in-test gate so `examples/` empties entirely?
- **Where does the helper author the gate body, and is that path wired or named?** When the helper authors a `bun` gate on demand, where does the file land (a per-engineer gates directory under the config home, a repo-local `.regimen/gates/`, somewhere the planner can root the command at), and does the helper create that location or point the engineer to it? This is the Enforcement analog of the Guidance helper's open "where does the find branch search" question.
- **How much of the silent-mechanism breadth does v1 actually enact versus name?** The emit-capable mechanisms (Group A gates, the Group D content gate) are the package's home turf and fully enactable today. The silent mechanisms (permission rules, sandboxes, CI checks, pre-merge gates, substitution) are real Enforcement and belong in the taxonomy, but several live outside any file Regimen authors (an OS sandbox, a host branch-protection rule). Does v1 author-and-wire the in-repo emit-capable mechanisms and only *name plus point* the rest, or does it attempt to wire the harness-permission and CI mechanisms too?
- **Should any silent mechanism gain an emit wiring it does not have today?** A pre-commit hook runs locally and *could* append a denial across the same seam; a CI bridge could record a rejection back into the store. None of these emit today. Is closing some of those emit gaps worth it for beat-3 validation, or is "the pattern abated in the conversation" enough validation for the silent mechanisms?
- **Official sign-off on the parallel act-beat operator skill per lever and the exact package shape.** The Guidance design and this one both lean firmly to one act-beat operator skill per lever package (Guidance in `packages/guidance`, Enforcement in `packages/enforcement`), with the shared planner extracted to `@regimen/shared`. The principle is agreed across both designs; the remaining call is the exact bundling mechanism (a shared skill bundler the levers compose into the one `regimen install`, versus a per-package `*Install` that lays down its own skill) and the formal sign-off.
- **Does the harness-permission mechanism (Group B) get a stronger-surface adapter?** The live `rm-rf` gate notes that a PreToolUse hook is bypassable on some Codex shell paths and that Codex's `PermissionRequest` hook is the stronger surface. If the helper is to pick the *strongest available* mechanism per harness, does the package need a per-harness "strongest enforcement surface" fact (an extension of `GATE_PROFILES`), or does the helper reason about it from the harness contract on demand?
